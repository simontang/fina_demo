# AI-native BI 架构评审交接稿

- 整理日期：2026-09-05。
- 面向：zcode 或其他独立架构评审者。
- 范围：Agentic Semantic Factory v0.2，以及吸收 Snowflake VQR、Databricks Genie benchmarks、dbt Copilot/Wizard 后的 AI-native BI 增补。
- 状态：设计已整理，新增治理、版本化运行时、问题评测与建模 Copilot 尚未实现；不代表客户已确认待定口径。
- 使用方式：本文可独立阅读，不依赖原始聊天记录或本地仓库。官方资料链接用于核对产品机制，不是完成评审的前置条件。

## 1. 评审任务

目标是构建 AI-native BI，而不只是聊天查数工具，也不只是自动生成 SQL 的建模流水线。

请检验：这套设计能否把业务知识、数据模型、交互分析和持续验证连成可落地的闭环；哪些约束必要，哪些过度设计，哪些关键能力仍然缺失。

建议按以下格式反馈：

1. 总体判断：方向、最重要的缺口、是否适合进入首个试点。
2. 按严重程度排列的问题：引用本文章节，描述具体失败场景与最小修正。
3. 应保留、应修改、应延后的设计，各给出理由。
4. 最小端到端实施切片：组件边界、必要契约、验收用例和依赖顺序。
5. 尚需业务方或工程团队提供的证据。

不要把设计提案当成已经实现，不要把合成样例当成客户事实，也不要因为本文已选择某项方案就默认接受它。可以挑战方案，但请说明替代方案如何满足对应约束。本次是评审材料，不授权安装产品、部署服务或操作生产数据。

## 2. 产品目标与现状

### 2.1 目标用户体验

业务用户可以提出“本月销售为什么下降”等问题。系统需要识别比较期间、核对指标口径和数据可用性，执行贡献分析及必要下钻，展示可解释的图表和证据，并允许继续追问、保存、刷新。

遇到缺失或冲突口径时，系统能够澄清，并把需要长期解决的问题交给语义资产生产流程，而不是临时编造定义。正确且可复用的分析方法经审阅沉淀，后续版本持续接受业务问题测试。

### 2.2 现有基础与证据边界

团队已有 Node Agent 网关、Java metrics-server、Python 服务、PostgreSQL、文档解析及相关数据接入能力。客户项目中人工完成过数据诊断、导入、SQL 视图建设、指标发布、业务知识整理和对账。

这能证明人工链路具有实践基础，不能证明自动 Agent 流程、严格多租户治理或可恢复发布已经成立。历史人效观察不是经控制变量验证的效率基准，不承诺倍数提升。

| 类别 | 当前判断 |
|---|---|
| 已有能力 | 指标查询与元数据服务、Agent 网关、项目 SQL/发布脚本、业务 KB 和历史对账材料 |
| 先前源码核查发现 | 部分 grants 是 datasource 级；存在空授权/legacy 回退；meta/KB 未形成统一不可变发布；有内存队列参与工作流 |
| 已形成设计 | Decision/Spec/ChangeSet、语义发布协议、已验证分析库、问题评测、Builder Copilot、AgentRelease |
| 尚未实现/验证 | 新 Governance API、严格版本查询、组合发布、dbt runner 闭环、独立问题评测和厂商工具集成 |
| 本稿未执行 | 线上权限验证、客户数据重算、模型调用性能测试、产品安装或部署 |

源码核查结论来自先前工作区检查，不是本稿新做的线上审计；落地时仍要对目标分支和环境重新验证。

## 3. 对早期方案的关键修订

以下早期假设不应继续作为评审前提：

| 早期假设 | 当前设计 |
|---|---|
| 原地替换 view 后，未点击发布就不会影响用户 | 已发布 meta 仍会访问被替换对象；默认使用隔离候选关系，验证后切版本 |
| dbt 模型只是 SELECT，执行风险有限 | hooks/macros 等也能执行代码；必须有数据库、进程、凭据与资源隔离 |
| `dbt build` 退出成功即完成验收 | 要核对必跑模型/测试、跳过项、独立预期与对账，不能只看退出码 |
| manifest 就有完整列级血缘 | 首版以资源依赖闭包为主，未知列级影响必须披露 |
| 静态页面回传 confirmed 就是客户批准 | 页面只提交答复；受信服务核验身份、授权、内容版本后生成批准回执 |
| 一个项目 stage 能驱动所有工作 | 项目是容器，多个 ChangeSet 可以并行，旧版本仍能服务 |
| 七态 business_status 已经代表完整状态机 | 拆分定义状态、用途、验证状态、重审状态和限制，原字段仅兼容保留 |
| 配置唯一 active 参数行即可 | BusinessRun 是版本化业务参数，同一项目允许多个 run 共存 |
| 全部数据计算都要先变成正式模型 | 正式数据生产仍受治理；受限探索计算可作为 AnalysisRun 派生结果，不能冒充正式指标 |
| 工作流接了持久化组件就证明可恢复 | 需要 job/outbox/幂等/失租等故障测试，不能从依赖名称推断恢复能力 |

## 4. 总体架构：资产生产与分析消费两个闭环

```text
资产生产闭环
数据/口径变化 -> ChangeSet -> 诊断与证据 -> 业务确认 + Semantic Spec
  -> Builder Copilot -> 隔离模型构建 -> 独立模型 QA
  -> 冻结语义版本 + 固定 Agent 版本 -> 问题评测
  -> 发布批准 -> 原子激活完整组合

分析消费闭环
业务问题 -> 身份与 QueryContext -> 检索适用的已验证方案
  -> 参数绑定或受约束规划 -> 语义查询/分析工具
  -> AnalysisRun + Claim + 图表 -> 追问/保存/刷新
  -> 反馈复核 -> 新方案候选 / 开发回归题 / ChangeSet
```

不要求每个用户问题走建模审批；不允许把临时分析结果直接发布为受信业务口径。数据刷新、业务定义变化、Agent 配置变化是不同变更类型，需要不同验证范围。

### 4.1 组件边界

| 组件 | 职责 | 禁止承担的职责 |
|---|---|---|
| Node Agent 网关 | 对话、计划、工具编排、进度、答复接入 | 自行确认业务定义、授予权限或独立切正式版本 |
| Java Governance/Release 增量模块 | 决策、批准、版本注册、原子激活、严格查询上下文 | 执行 LLM 生成代码或直接运行 dbt |
| 隔离 CLI runner，后续可服务化 | 锁定输入、构建/测试、有限修复、返回工件与回执 | 修改批准、选择客户默认口径、直接发布 |
| PostgreSQL 控制库 | revision、gate、job、发布指针、outbox | 向 Builder 暴露管理凭据或控制表 |
| 数据面 | 封存 landing、候选关系、已发布关系 | 允许构建账号继续改写已封存对象 |
| 工件存储与 Git | 候选代码、Spec、测试、KB、版本化证据 | 让导出 JSON 或聊天内容绕过正式接受流程 |
| Analysis Agent | 读取获准语义资产，执行受限分析，组织证据答案 | 任意物理 SQL、任意部署或放宽评测标准 |

这些是职责划分，不是要求新增同等数量的服务。首版可以沿现有宿主增量实现；拟议 Governance 模块目前不是已存在的完备能力。

### 4.2 核心对象

| 对象 | 解决的问题 |
|---|---|
| SourceSnapshot | 本次计算用了哪份数据，是否封存、可追溯、仍保留 |
| BusinessRun | 日期、阈值等业务参数是哪一版；不是一次技术执行 job |
| DecisionRevision | 谁在何范围内，依据什么证据确认了什么选择 |
| SemanticSpecRevision | 明确粒度、公式、聚合顺序、过滤、时间、单位、null/重复规则与样例 |
| ChangeSet | 本轮变更基于哪版、影响什么、需要哪些确认和验收 |
| GateReceipt | 服务端核验后生成的具体批准记录；撤销另记事件 |
| SemanticRelease | 数据/参数、模型、指标、Spec、KB 和资源范围的不可变组合 |
| VerifiedAnalysisRecipe | 经验证的分析方法及其适用条件，不是固定答案 |
| QuestionCase / EvaluationRun | 可重复执行的业务测试，以及逐题证据和结果 |
| AgentRelease | 模型、prompt、工具/编排、检索、方案和回答规则版本 |
| DeploymentBinding | scope 内默认启用的语义版本与 Agent 版本组合 |
| AnalysisRun / Claim / Workbook | 实际分析过程、带证据的结论、可刷新分析定义，分别存储 |

## 5. 吸收 Snowflake VQR：已验证分析库

### 5.1 官方机制与设计借鉴

Snowflake VQR 保存问题及经核对的 SQL，用相关示例帮助回答相似问题；SQL 引用语义模型逻辑对象。作者仍需核对其正确性。它不是结果缓存，也不等于命中后新答案必然正确。[官方 VQR 文档](https://docs.snowflake.com/en/user-guide/views-semantic/verified-query-repository)

我们的适配不是复制一个物理 SQL 库，而是把专家验证的解题方法结构化为 VerifiedAnalysisRecipe。

### 5.2 Recipe 内容与生命周期

一条方案包含：

- 标识、revision、digest、tenant/project、业务场景。
- 问题意图、同义问法、术语、question family。
- 适用指标与 Spec semantic_digest、粒度、单位、时间规则、定义状态。
- 参数类型、范围、必问项和允许的缺省依据。
- 语义查询或工具计划、分支、停止条件、输出要求。
- 可以表达的结论类型和已知限制。

验证/审阅回执在内容冻结后按 digest 关联，不进入被验证内容自身的摘要。批准与撤销由治理记录管理，AgentRelease 引用获准方案快照，不引用可随意修改的 latest 目录。

运行规则：先按身份和语义版本筛选，再检索；明确命中且参数完整时直接实例化方案；存在口径歧义时澄清；未命中时可以受限规划，但新方案不能自动标记 verified。

所有计划仍经过服务端语义编译、参数验证和当前授权。历史查询数值不能替代当前执行。指标语义变化要检查旧方案是否失效；跨客户只能复用去项目化的方法模板，不能混入客户实体、数据或查询明细。

### 5.3 RAG 与预加载

首版采用结构化 ID/术语匹配和全文检索，不强制 embedding，也不认为必须先建向量数据库。

持久化对象是受治理的记录和版本工件；内存只是可重建的索引/缓存。预加载已批准的定义、方案和必要项目元数据，按内容版本刷新。客户明细默认按权限实时读取，不全量塞进 prompt 或持久化 KB。

后续 embedding 只能改善候选召回，不能代替权限、口径兼容性和批准判定。缓存必须隔离 scope、版本、输入及权限上下文，命中后仍重检当前撤权和暂停状态。

## 6. 吸收 Databricks benchmarks：问题级评测

### 6.1 官方机制与设计借鉴

Genie benchmarks 把业务问题与参考答案作为可重复测试。Chat 模式比较查询结果；Agent 模式用 LLM judge 评价多步骤回答。官方建议覆盖同义问法，每题默认开启新会话，因此多轮正确性需要另测。[官方评测文档](https://docs.databricks.com/aws/en/genie-agents/monitor)

我们吸收“评价用户问题的实际结果”，不直接照搬其全部判分规则。模型测试、问题测试、上线监控是不同层次，不能互相替代。

### 6.2 三类数据必须隔离

| 集合 | 用途与可见性 |
|---|---|
| 已验证分析库 | Runtime 在当前授权范围内可见，用来指导分析 |
| 开发回归集 | 开发者和修复 Agent 可见，用于定位失败和验证修复 |
| 独立保留测试集 | 独立 evaluator 与授权评审者可见，用于未暴露题目的评价 |

按问题族划分，不能将同一题的改写分别当教学样例和独立试题。保留题答案、参考 SQL 不能进入 Agent 可读 KB、索引或工作目录；执行测试时只提交该 case 的问题/合法会话输入。因诊断披露给修复 Agent 的题转入开发集，并补充新的保留题。

冷启动没有足够保留题时，如实报告只有开发回归，不宣称已验证泛化。

### 6.3 每个测试需要固定什么

QuestionCase 固定问题/会话脚本、测试身份、数据/参数、期望行为、独立预期、断言、风险和时延预算。期望行为可以是回答、澄清、拒绝或说明不可用，不是所有题都必须给数字。

EvaluationRun 记录 Suite/评分策略、两类 release、数据/参数、evaluator/compiler/tool 版本，以及逐题输出、耗时、成本和差异。不能只留一个总准确率。

| 检验层 | 关键断言 |
|---|---|
| 权限 | 跨租户/项目、缓存与工具旁路、提示注入；越权为硬失败 |
| 语义 | 指标、粒度、过滤、期间、单位、分母和聚合顺序 |
| 数值 | 独立结果；金额精度、NULL/0、重复行、合法空集、Top-K/并列规则 |
| 表达 | 答案数值/来源一致，限制清楚，不把贡献分解说成因果 |
| 图表 | 数据绑定、系列映射、轴/单位、筛选和下钻继承相同 context |
| 交互 | 多轮切换、正确澄清、刷新、超时、取消和错误恢复 |

LLM judge 只辅助评价文字和相关性，不替代金额及授权断言。生成参考 SQL 也要复核，不能让同一错误同时生成实现与唯一测试预期。

必跑题缺失/SKIP 不计 PASS；非确定性题记录重复运行波动；阈值在正式对比前登记。删题、改 ground truth 或放宽标准须独立审阅，不能静默迎合候选。报告开发集与保留集成绩、关键错误、时延和成本，而非一个混合分数。

## 7. 吸收 dbt Copilot/Wizard：Builder Copilot

### 7.1 能力区分

截至前轮官方资料核对，Copilot 提供 SQL、测试、文档、语义模型等生成辅助；Wizard 面向更完整的项目调查、开发和验证。二者不是简单同名替换，也不能把托管能力等同于 dbt Core 内置功能。[Copilot 概览](https://docs.getdbt.com/docs/dbt-ai/copilot-overview)

值得吸收的是项目上下文驱动、影响分析、生成与验证联动。Wizard 使用项目元数据理解工作并规划验证；我们的普通 dbt artifacts 不应因此被宣称具备相同的完整列级血缘能力。[Wizard 工作机制](https://docs.getdbt.com/docs/dbt-ai/wizard-how-it-works)

### 7.2 拟议工作流

```text
读取已接受 Decision/Spec 与 ChangeSet
  -> 加载/刷新项目元数据索引
  -> 确定依赖闭包、影响指标和回归题
  -> 生成 SQL + schema + tests + docs + meta 的连贯 patch
  -> 受限开发 target 中 parse/compile/build
  -> 读取实际错误并按预算有限修复
  -> 独立 QA、变更 diff、限制说明
  -> 交给治理服务审核发布
```

现有 SQL 是实现证据，不是业务口径的唯一权威。未确认定义必须回到澄清流程。Builder 不能自行批准、扩权、改最终验收预期或直接覆盖正式关系。

元数据索引按代码/artifact 版本刷新；依赖未知时标注并扩大验证，而非假定没有影响。预加载可能降低准备开销，但模型首输出、排队、构建和修复时延仍需实测。

### 7.3 复用策略

| 路径 | 当前建议 |
|---|---|
| 自有 Agent + dbt CLI/artifacts | 首版基线，沿现有工程增量实现 |
| 官方 dbt skills | 固定版本、检查权限与约束后选择性适配；不整包无条件引入 |
| dbt MCP | 可作 adapter；Builder 和 Runtime 工具白名单分开；协议不替代鉴权 |
| Wizard headless | 作为后续对比候选；验证沙箱、输出契约、版本和供应商兼容后决定 |
| 托管 Copilot | 可供工程师辅助开发，不作为我们的必选运行时依赖 |

官方 [skills 仓库](https://github.com/dbt-labs/dbt-agent-skills)包含多类建模技能，但 MetricFlow 语义定义不是现有 Java metric meta 的直接替代。[MCP 官方文档](https://docs.getdbt.com/docs/dbt-ai/about-mcp)区分本地 CLI 能力和远程托管工具；[Wizard headless](https://docs.getdbt.com/docs/dbt-ai/wizard-headless)可结构化输出，前轮核对时仍标记 Beta。以上均未在本项目安装或验证。

首版不以 LangChain、ReAct 或 deep-agent 产品名作为架构保证：简单已验证问题走参数化执行，复杂分析使用有预算、终止条件、取消机制的工具循环；建模是独立开发工作流。具体编排框架仍需按现有代码和可测收益选择。

## 8. 可信发布：语义版本与 Agent 版本同时固定

### 8.1 为什么要两类版本

SemanticRelease 锁定业务定义、数据/参数、模型、catalog、资源范围及 KB。AgentRelease 锁定模型配置、prompt、工具/编排实现与策略、skills、Recipe 快照、检索与回答/图表规则。

同样 SQL 和数据，换 prompt 或模型也可能答错，因此 active pointer 应是完整组合：

```text
DeploymentBinding = (
  tenant_id, project_id, environment,
  semantic_release_id, agent_release_id, activation_revision
)
```

AgentRelease 不保存密钥或冻结用户权限。外部供应商若更新同名模型，要记录可取得的版本/fingerprint 并监测；仅固定模型名不足以承诺逐字复现。

### 8.2 决策批准不能脱离业务内容

业务批准绑定预览、选择和 Spec 的 semantic_digest。业务摘要覆盖粒度、公式、聚合顺序、过滤、时间、单位、null/重复和参数约束；排除来源引用、验收回执及摘要本身，避免自引用。完整 Spec 另有内容摘要。

静态 HTML 只回传答复。服务端依据受信身份/授权、登记预览与答复证据接受 DecisionRevision；离线答复由授权核验者见证，不冒称客户数字签名。批准、撤销与激活需按同一 scope 串行检查，Agent 不能修改这些权威记录。

### 8.3 构建、评测、批准的依赖顺序

```text
已接受 Decision/Spec + 锁定代码/输入
  -> 隔离构建并封存模型
  -> 模型 QA
  -> 编译 KB，冻结 SemanticRelease

经验证方案 + Agent 配置 -> 冻结 AgentRelease

两类冻结 payload + 固定 Suite/数据/参数
  -> 外部最终验证及 EvaluationReceipt
  -> 发布预览与批准
  -> 同一控制事务重检并 CAS 激活 tuple
```

关键约束：

1. 模型 QA 可作为后续 KB 输入；最终 release/问答回执不能写回它所验证的 payload 或 KB，避免摘要环。
2. EvaluationReceipt 绑定两类 payload 摘要、Suite/评分策略、数据/BusinessRun 和执行证据。
3. 发布/回退预览、批准和 activation envelope 必须绑定具体 evaluation_receipt_digest；同一 tuple 替换评测证据也须重新批准。
4. 控制事务内核对预期 active revision、候选、业务批准、readiness、兼容性、具体评测回执、当前撤销/权限，再更新唯一指针及 outbox。
5. 远程构建/LLM 不放进持锁事务；控制指针原子切换不是跨数据库分布式事务。
6. 只改 Agent 可以复用未变语义资产的有效批准，不必重建 dbt，但新组合仍需问答评测和发布批准。

### 8.4 在途查询、回退和恢复

QueryContext 由服务端保存或签发，固定语义/Agent 组合、数据、BusinessRun、KB 和 TTL。同一 AnalysisRun 的查询、检索和工具调用不混版；上下文过期或历史数据不可用时明确中止或开始新 Run，不能静默切 latest。

回退也是一次新 CAS activation：目标为历史完整 tuple，基于当前 active revision 生成新预览、rollback 授权及适用验证。历史发布批准的提交期限不应阻止合法的新回退；但新政策禁止的旧口径、prompt、工具或已删除数据仍不得恢复。

实时授权始终优先：历史 release 只限定可用资源上限，不能复活被撤销的权限。旧单 release API 不得绕过组合检查。

执行采用 at-least-once 投递、持久 job/outbox、幂等键、独立 attempt、租约和 fencing。重复投递不重复发布，失租 worker 不得覆盖新执行；不假设框架天然保证 exactly-once。

## 9. 数据、权限与分析体验的边界

- 身份由认证和项目登记决定，不能由普通 header 自授 tenant/project；strict scope 空 grants 拒绝，不自动退回 legacy。
- 正式模型依赖封存输入与版本化关系。仅给对象加版本名称不够，还要收敛 ownership/写权限，阻止旧构建账号继续修改。
- dbt/macros/hooks 视为可执行代码。控制面与数据面分权，生产与开发凭据分离，执行环境限制网络、资源、目标 schema 和危险操作。
- 参考 SQL 允许存在于受限建模/评测工件，不自动开放给运行时。临时计算不能借“探索”绕过数据授权或发布治理。
- Claim 分清事实、贡献分解与因果假设；结果正确但依据错误仍应失败。
- Workbook 保存分析定义和图表规范，刷新生成新 Run，不覆盖旧证据。对话、表格、图表、筛选、下钻与保存应共用分析上下文。

AI-native BI 的语义计算扩展、复杂诊断方法、行列级权限、导出治理、订阅监控及行动执行尚未完整设计。这些是待评审缺口，不应被上述对象命名掩盖。

## 10. 首批试点及合成判别样例

### 10.1 New Order Gap：验证业务决策到答案

现有项目存在 Action Gap 与 Signed Gap，默认业务口径仍待客户确认。保留两个指标的原语义，不能静默改变已有 ID 的定义。

```text
match_key = canonical_sales x sold_to x product
required(key) = won_y1(key) * threshold
signed_gap(key) = required(key) - matched_order(key)
action_gap(key) = max(signed_gap(key), 0)
```

项目与订单先分别汇总到匹配粒度再 join，避免明细放大。

| 合成记录 | Won Y1 | threshold | Matched Order | Required | Signed Gap | Action Gap |
|---|---:|---:|---:|---:|---:|---:|
| A | 100 | 0.5 | 40 | 50 | 10 | 10 |
| B | 100 | 0.5 | 80 | 50 | -30 | 0 |
| 合计 | 200 | 0.5 | 120 | 100 | -20 | 10 |

合计后再 clamp 得 0，是错误的 Action 总额。只问“缺口多少”且没有默认定义时，应澄清或并列明确标签；用户从 Action 追问 Signed 时，应切换语义计划，不能沿用旧指标。

这个试点证明治理和消费一致性；因为两种公式已经存在，单凭它不能证明新模型自动生成能力。

### 10.2 Sell-in NES：验证模型生产

在隔离项目中回放 Team 白名单与 GMM 排除规则，选择一个 `SUM(nes)` 模型，单位为人民币。测试 Builder 生成/修改模型、配套 tests/docs、实际构建和独立对账。

已有历史观测只有在对应输入快照、期间、单位和精度一致时才能作为精确基准；拿不到匹配快照就使用明确合成 fixture，并记录历史大样本复现缺口。不能把历史已确认规则伪装成新客户批准。

## 11. 最小实施顺序

| 阶段 | 最小工作 | 完成依据 |

首版不强制向量数据库、通用 DAG 引擎、独立图数据库、全量列级血缘、复杂多 Agent 平台或托管 Copilot。先证明一条治理链和一个模型修改闭环。

## 12. 必须覆盖的验收场景

以下都是待执行测试，不是已通过结果。

| 编号 | 场景 | 预期 |
|---|---|---|
| BI01 | 命中已验证方案后改变合法参数 | 执行新查询，记录方案版本，不复用历史答案 |
| BI02 | 未确认默认 Gap；随后明确 Action/Signed | 先澄清/并列，再分别得到合成结果 10/-20 |
| BI03 | 单位、粒度、时间或 Spec 变化 | 旧方案不能未经兼容检查自动使用 |
| BI04 | 跨 scope 检索、撤权后读缓存 | 返回内容前拒绝，缓存不能绕权 |
| BI05 | 同问题族跨教学/保留集，或修复 Agent 读取答案 | 检测泄漏；披露题转开发集，重新计覆盖 |
| BI06 | 错误聚合、明细 join 放大、阈值硬编码 | 独立样例与问题测试捕获错误 |
| BI07 | NULL/0、合法空集、截断结果、Top-K 并列 | 按契约区分，不笼统宽松匹配 |
| BI08 | 只换 prompt/模型，同时发生并行发布 | 新 AgentRelease、评测及 tuple CAS，无旧 API 旁路 |
| BI09 | 删题、SKIP、改预期或 LLM judge 单方面放行 | 必跑缺失不通过，策略变化有独立批准 |
| BI10 | Builder 索引过期、依赖未知、测试漏跑 | 刷新/扩大验证或阻止通过，披露缺口 |
| BI11 | 源码/文档诱导扩权、改 gate 或原地发布 | 环境和服务端拒绝，不只依赖 prompt |
| BI12 | 多轮中激活新版、context 过期或旧数据删除 | 同 Run 不混版，不可继续时明确处理 |
| BI13 | 数值正确但单位、因果表述或图例映射错误 | 表达/图表验收失败 |
| BI14 | 模型超时、取消、重试和非确定性波动 | 有明确结果与成本记录，不暗中换模型 |
| BI15 | 回退目标包含已禁用 prompt/工具/方案 | 拒绝，不借合法语义版本恢复风险 |
| BI16 | 同 tuple 在批准后替换评测回执 | 原批准失效；验证、批准、激活证据摘要一致且无环 |

另有基础治理故障测试：伪造批准、内容审阅后变更、nonce 冲突、撤销与激活竞争、构建半途失败、KB 未就绪、旧账号改封存对象、重复投递、旧 worker 回写和输入快照丢失。

评测报告分别显示开发/保留题、关键错误、正确澄清/拒答、证据覆盖、p50/p95 时延和成本。人效以“验收通过的变更”为单位，分开记录人实际投入、机器耗时、等待批准、返工和平台维护成本。

## 13. 请重点挑战的架构问题

1. **产品完整性**：是否仍然偏重资产生产，缺少让业务用户持续使用的分析工作台？首版最重要的交互是什么？
2. **语义表达能力**：现有聚合/比率加 dbt 模型能否支持时间智能、非可加指标、层级、多事实表分析？扩展边界在哪里？
3. **探索与治理**：临时计算如何不冒充正式指标？哪些分析可以自动执行，哪些要业务确认或技术 review？
4. **Recipe 复杂度**：首版是否只应支持参数化语义查询，而把复杂分支留给通用分析 Agent？怎样判断适用性而不误匹配？
5. **测试独立性**：如何在小样本场景建立真正独立的预期与保留题？如何防止反复调参后只剩“背题通过”？
6. **判分可信度**：数值正确但口径错、答案合理但证据不足，分别怎样自动识别？LLM judge 的边界是否足够清晰？
7. **发布复杂度**：SemanticRelease + AgentRelease + tuple 是否合理？能否简化而仍保证同一答案不混版和评测证据不可替换？
8. **数据刷新成本**：每日数据更新是否都需完整评测？哪些模型/方案受影响，怎样安全复用既有证据？live 模式如何定义一致性？
9. **权限与证据保留**：多源行列级权限、导出、缓存、历史答案和删除请求如何协同？当前 scope/grants 设计遗漏什么？
10. **dbt 复用范围**：哪些能力用 CLI/artifacts 就够，哪些值得引入 MCP、官方 skills 或 Wizard？如何衡量依赖成本与实际收益？
11. **Agent 运行机制**：简单执行、受约束工具循环与多步骤建模如何路由？预加载、超时、取消、重试和失败恢复的最小实现是什么？
12. **实施顺序**：P2 是否过重？请给出更小但不绕过安全和版本约束的第一条纵向切片，并明确验收证据。
