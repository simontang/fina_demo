# 业务自助的边界：哪些真的能交给业务

- 状态：draft v0.1
- 回答的问题：相对于传统数仓"业务+IT 反复"，本方案能否让业务在 AI 帮助下自己制作指标、报表、视图？
- 关联：[README](./README.md)、[etl-vs-sql-cleaning.md](./etl-vs-sql-cleaning.md)、[open-questions-recommendations.md](./open-questions-recommendations.md)

## 0. 核心判断

方向成立，但准确的表述不是"去掉 IT"，而是 **IT 从生产者变成轨道维护者**。传统数仓的痛点是业务与 IT 在队列里反复：业务提需求 → IT 排期 → 做出来不对 → 再排期。本方案把这个循环拆成"业务在治理好的轨道上自助 + IT 预先铺好轨道"。

为什么这次能成而经典自助 BI（Tableau/PowerBI 语义层）大多失败：**治理被预先支付了**。自助 BI 失败的原因不是工具难，而是没有状态机（draft 冒充 confirmed）、没有测试（错误静默上线）、没有决策捕获（口径散落在会议纪要）、没有权限边界（人人直连大宽表）。这套架构的十条原则恰好把这四件事变成了基础设施——业务+AI 是**在有护栏的场地上开车**，不是在旷野里开车。

## 1. 四层自助边界

按"离现有资产的距离"分层，自助程度递减：

| 层 | 任务 | 谁做 | IT 参与 | 依据 |
|---|---|---|---|---|
| T1 组合与消费 | 新报表、新分组筛选、新看板、即席分析 | **业务 + AI，完全自助** | 零 | runtime 三件套（meta + metrics/query + KB）就是为此设计的 |
| T2 新指标（现有 view 上） | 派生指标：比率、缺口、同比环比 | **业务 + AI，轻量 gate** | 审一眼发布预览 | SQL-free metric meta 的设计初衷：聚合/比率不写 SQL，发布即上线 |
| T3 新视图/新加工 | 新语义视图、新 match 逻辑 | **业务分析师 + AI 起草，人审 gate** | 评审，不代写 | dbt model + test 成对生成；decision 捕获口径；对账自动验收 |
| T4 新源与架构 | 新 datasource、grants/角色、跨源建模、性能 | **IT** | 全程 | 安全边界（security-notes）与成本/架构判断不可外包 |

关键点：T2 之所以接近全自助，是因为"指标发布不需要写 SQL"在这个架构里是设计出来的性质（P8），不是巧合。T3 是分水岭——业务分析师 + AI 能做，但 test 必须成对生成、对账必须过，不能因为发布者变成业务就放松。

## 2. 瓶颈的转移（这是真正的收益）

- 传统模式：瓶颈 = **IT 排期**，随 IT 人数线性受限；业务处于被动等待。
- 本方案：瓶颈 = **确认/评审 gate**，随业务自己的注意力扩展；IT 人数不再决定业务吞吐。

注意这不是零成本：gate 依然要人花时间。但 gate 的时间花在"业务拍板自己的口径"上——这件事本来就该业务做，而且没人能替他们做。

## 3. 对组织的要求（"交给业务"的真实前提）

1. **业务侧需要一个新角色**：不是最终用户，而是"业务数据负责人"——懂口径、有权拍板、愿意确认。Hankel 的 `evidence/responses/*.json` 证明这个角色已经存在：11 条待确认口径本来就是客户业务方答的。工厂只是把"答复之后等 IT 实现"的半段折叠掉了。
2. **自助 ≠ 自治**：状态机、test 成对、发布 gate 对业务发布者**同样强制**。最大的失败诱惑是把 gate 关小来"提升自助体验"——那一步迈出去，就回到自助 BI 的指标混乱老路。
3. **IT 的残余职责**：维护模板、评审 T3、铺新轨道（T4）、看护平台。单项目 IT 投入显著下降，但平台投入上升——人效来自"一套轨道服务 N 个项目"。

## 4. 失败模式（诚实清单）

1. **gate 摩擦失衡**：调太高 → 退回 IT 队列，白建；调太低 → 口径通胀，两个"销售额"并存。
2. **无权限的人拍板**：不完全拥有口径的业务用户把 draft 确认为 confirmed——决策捕获装置必须校验参与者角色（manifest.participants 的 client_confirmer）。
3. **弱测试放行错翻译**：AI 把业务语言翻成 SQL 时出错且测试太弱 → 错误指标静默上线。test 强制成对 + 对账基线是底线。
4. **冷启动被忽略**：自助运行在一个**播种过的花园**里——landing、初始语义模型、KB 骨架仍是 IT 重活。"完全交由业务"只对已 onboard 的项目成立。

## 5. 验证方式

把它当成一个可测的假设：M5 基准（Dashboard 20 指标流水线）之外，加一个**业务操作者测试**——请 Hankel 项目真正的口径确认人（非 IT），在 AI 协助下新增 1 个指标（T2）和 1 个视图（T3），记录：完成耗时、IT 介入次数、test 是否成对、是否走了正确的 gate。通过标准：T2 零 IT 介入、T3 仅评审介入。这个测试通过，"交给业务"才从愿景变成事实。
